# RailMind：全空间、动静结合的列车智能运维智能体平台

> 最终开发方案 V1.0
>
> 整理日期：2026-09-04

---

## 1. 项目概述

### 1.1 项目背景

高速列车安全运行涉及车顶受电弓、走行部传动系统、车底外露结构、车内环境以及线路侧设施等多个空间。现有检测系统通常按照专业分别建设，例如振动监测、受电弓监测、车底视觉巡检、车内视频监控和线路异物监测等，各系统能够发现局部异常，但数据格式、接口方式和诊断结论相互独立，难以形成统一的风险研判和运维闭环。

RailMind 拟建设一套位于既有列车控制和监测系统之上的开放式智能运维平台。系统**不替代** CTCS、ATP、ATO、联锁、调度和车辆控制系统，**不直接控制**制动、牵引、车门和受电弓升降，而是完成：

- 多源数据接入、专业模型诊断、开放能力编排、多 Agent 协同、RAG 知识检索、检修辅助决策和工单闭环。

项目重点不在于重新制造全部检测设备，而在于将已有模型、开源模型、规则算法、企业既有系统和后续新增能力，通过统一接口接入同一套智能体平台。

### 1.2 项目定位

项目面向三个业务阶段：

| 阶段 | 主要数据 | 重点能力 |
| --- | --- | --- |
| 列车运行中 | 振动、电流、电压、温度、车内视频 | 传动系统诊断、受电弓电弧、车内异常筛查 |
| 进站停靠或低速通过检测点 | 车底、车轮、受电弓等图像 | 包覆结构、检查门、车轮表面缺陷、受电弓磨耗 |
| 线路侧任务 | 固定监控、巡检图像、无人机影像、外部告警 | 轨道异物、接触网或线路环境异常（可选实现） |

项目**不设置入库检修场景**。

### 1.3 总体目标

构建一套覆盖车顶、走行部、车底、车内和线路侧的智能运维原型，实现：

1. 多类模型和监测模块的统一接入；
2. 模块在平台运行过程中动态注册和加载；
3. Chief-Agent 根据车辆状态和任务动态选择能力；
4. 专业 Agent 对领域内结果进行综合分析；
5. RAG 知识库提供规程、案例和检修步骤依据；
6. 高风险事件经过人工确认后生成工单；
7. 模块失效时支持拒判、降级和主备切换；
8. 前端完整展示车辆状态、诊断证据、Agent 结论和工单过程。

### 1.4 项目成果边界

项目成果分为三类。

**已有能力工程化**

- 车底包覆结构检测；
- 检查门闭合状态检测。

**开源资源复现和集成**

- 列车传动系统故障诊断；
- 受电弓滑板磨耗分类；
- 车轮表面缺陷分割；
- 可选的线路侧视觉能力。

**通用模型和模拟数据原型**

- 车内多帧 VLM 异常筛查；
- 受电弓电弧波形原型；
- 外部车门或其他模块热加载演示；
- 车辆运行状态和进站状态模拟。

系统必须明确说明：**公开数据和模拟数据验证不等同于真实高速动车上线认证**。

## 2. 需求分析

### 2.1 用户角色

| 角色 | 职责 |
| --- | --- |
| 运维管理员 | 查看车辆整体状态、实时告警、专业 Agent 状态、能力模块健康度和工单进度 |
| 检修工程师 | 查看诊断证据、风险结论、知识库引用和建议步骤，确认、修改或驳回工单草稿 |
| 算法与模型管理员 | 注册模型、设置适用场景、管理版本、执行在线测试、设置主用或备用能力 |
| 系统管理员 | 管理用户权限、数据访问、服务状态、日志和运行配置 |
| 外部能力提供方 | 通过 SDK、REST 接口、文件适配器或消息适配器接入既有模块，只能访问被授权的数据和任务 |

### 2.2 核心业务流程

**原始数据诊断流程**

```text
传感器、图片、视频或波形
        ↓
   数据接入与校验
        ↓
    查询能力注册中心
        ↓
 调用适用模型或专业Agent
        ↓
    生成统一诊断事件
        ↓
  Chief-Agent风险融合
        ↓
    RAG检索规程和案例
        ↓
       人工确认
        ↓
       工单闭环
```

**既有系统接入流程**

```text
中车或第三方既有监测系统
        ↓
    RailMind适配器
        ↓
     统一事件协议
        ↓
 Chief-Agent及平台服务
```

既有系统不需要重新训练模型，也不要求使用 Python，只需将结果转换为 RailMind 标准事件。

**外部能力热加载流程**

```text
    启动外部模块
        ↓
   提交能力描述文件
        ↓
   注册中心完成校验
        ↓
    心跳和健康检查
        ↓
  能力中心自动显示
        ↓
 管理员切换运行模式
        ↓
Chief-Agent动态发现并调用
```

整个平台不重启，Chief-Agent 主代码不修改。

### 2.3 功能需求

系统至少包含以下功能：

- 综合态势；
- 运行中诊断；
- 进站停靠快检；
- 车内巡检；
- 线路侧任务；
- 能力中心；
- 告警中心；
- 智能诊断详情；
- RAG 知识中心；
- 工单中心；
- 模型管理；
- 审计和系统监控。

### 2.4 非功能需求

| 维度 | 要求 |
| --- | --- |
| 扩展性 | 新模块不得写死在 Chief-Agent 内部，必须通过能力注册中心和统一协议接入 |
| 可维护性 | 每个模型独立服务化，拥有自己的依赖、配置、Dockerfile 和模型卡 |
| 可信性 | 所有结论保留数据来源、模型版本、置信度、关键证据、知识引用和人工确认结果 |
| 安全性 | 高风险结论不自动控制列车，不直接触发安全关键动作 |
| 演示稳定性 | 所有外部大模型和网络服务均需准备固定样例和本地降级路径 |

## 3. 总体技术方案

### 3.1 总体架构

RailMind 采用六层架构：

```text
    设备、传感器、图片视频、既有系统
                ↓
       开放能力接入与适配层
                ↓
       专业模型和诊断工具层
                ↓
            专业Agent层
                ↓
 Chief-Agent、风险引擎与RAG知识层
                ↓
   告警、工单、能力中心和前端展示层
```

### 3.2 开放能力接入层

开放能力接入层是项目的核心平台能力，包括：

- 能力注册中心；
- 能力描述协议；
- 统一诊断事件协议；
- 统一任务与回调协议；
- Python 接入 SDK；
- REST 适配器；
- 文件和对象存储适配器；
- Redis Streams 消息适配器；
- 数据库轮询适配器；
- 心跳和健康检查；
- 模块审核、启用、禁用和主备切换。

### 3.3 专业模型层

本期核心能力包括：

1. **Drivetrain-Agent**：传动系统复合故障诊断；
2. **Panto-Agent**：受电弓磨耗和电弧风险分析；
3. **Underbody-Agent**：包覆结构和检查门检测；
4. **Wheel-Defect-Capability**：车轮表面缺陷分割；
5. **Cabin-Agent**：车内短视频多帧 VLM 筛查；
6. **LineSide-Agent**：线路侧异常识别（可选实现）。

### 3.4 Agent 层级

系统中的能力分为三类。

- **信号源型能力**：只主动发送状态或异常，例如温度报警、烟雾传感器、车门状态和既有故障码。
- **工具型能力**：接受一次任务并返回推理结果，例如检查门检测、滑板磨耗分类、车轮缺陷分割和 VLM 视频分析。
- **专业 Agent**：能够调用多个工具、查询历史状态并形成领域结论，例如 Drivetrain-Agent 和 Panto-Agent。

Chief-Agent 位于所有专业 Agent 之上，负责全局协同。

### 3.5 推荐技术栈

| 层级 | 技术 |
| --- | --- |
| 模型 | Python、PyTorch、OpenCV、ONNX Runtime、NumPy、SciPy、FFmpeg |
| 后端 | FastAPI、Pydantic、SQLAlchemy、WebSocket |
| 数据库 | PostgreSQL |
| 事件与任务 | Redis Streams |
| 文件存储 | MinIO |
| 向量数据库 | Qdrant |
| Agent 编排 | 自定义状态机或 LangGraph 式工作流 |
| 前端 | Vue 3、TypeScript、Element Plus、ECharts |
| 部署 | Docker、Docker Compose、Nginx |

## 4. 数据集与数据治理方案

### 4.1 数据分级

所有数据资源登记为以下状态：

| 状态 | 含义 |
| --- | --- |
| AVAILABLE | 已下载并能够读取 |
| VERIFIED | 已检查标签、格式和许可 |
| PENDING | 有公开线索但尚未完成下载 |
| APPLICATION_REQUIRED | 需要申请或联系作者 |
| DEMO_ONLY | 模拟数据或演示视频 |
| INTERNAL | 团队已有数据 |

**未经验证的数据不能作为核心模块唯一依赖。**

### 4.2 核心数据资源

**车底包覆结构数据**

使用团队已有数据和模型，重新整理：

- 图片来源；
- 标注类别；
- 数据划分；
- 模型版本；
- 样例输入和输出；
- 适用场景。

**传动系统数据**

优先使用能够实际下载的列车转向架或传动系统公开数据，覆盖牵引电机、齿轮箱和轴承。在开发启动前先确认：

- 文件能够下载和解压；
- 标签说明完整；
- 采样频率明确；
- 数据读取脚本可运行。

**受电弓磨耗数据**

使用公开受电弓滑板图像和代码，完成数据清洗、迁移学习、分类和模型导出。

**车轮缺陷数据**

使用 FaultSeg 或其他能够实际下载的列车车轮缺陷数据，完成实例分割和缺陷面积计算。

**车内场景数据**

准备少量短视频场景，不训练大型专用行为模型：

- 正常乘车；
- 人员倒地；
- 通道堵塞；
- 行李占道；
- 疑似烟雾；
- 异常聚集。

**线路侧数据**

根据时间选取一个能跑通的任务，例如轨道异物或接触网外观异常。无人机只作为图片或视频来源，不开发飞控。

### 4.3 数据版本管理

Git 中只保存：

- 数据清单；
- 下载脚本；
- 数据许可证；
- 哈希值；
- 小型样例；
- 标注转换脚本。

大型数据、视频和模型权重保存在 MinIO 或共享存储中。

建议使用如下数据清单：

```yaml
dataset_id: pantograph_wear_v1
name: Pantograph Wear Dataset
status: VERIFIED
source_type: public_repository
license_status: research_use
storage_uri: s3://datasets/pantograph-wear/
sha256: "..."
tasks:
  - image_classification
```

### 4.4 数据安全

- 车内视频优先使用模拟或公开视频；
- 演示素材中不展示可识别个人身份；
- 外部模块只能访问任务指定文件；
- 文件下载使用短时授权地址；
- 所有访问和导出行为记录审计日志。

## 5. 核心模型设计

### 5.1 Drivetrain-Agent：传动系统复合故障诊断

**输入**

- 多通道振动；
- 三相电流；
- 转速；
- 温度；
- 车辆速度；
- 测点和部件信息。

**算法流程**

```text
原始时序 → 去噪与归一化 → 滑动窗口切片 → FFT或STFT
        → 多通道特征融合 → 1D-CNN或时频图分类
        → 单部件/多标签故障输出 → 置信度校准
```

**诊断对象**

- 牵引电机；
- 齿轮箱；
- 左右轴箱轴承；
- 复合故障。

**前端结果**

- 原始波形；
- 频谱；
- 部件风险条形图；
- 故障类别；
- 置信度；
- 关键频带；
- 历史趋势；
- Agent 综合结论。

**最低交付**

- 数据处理脚本；
- 训练脚本；
- 模型权重；
- 推理接口；
- 模型卡；
- Docker 服务；
- 样例正常和异常数据。

### 5.2 Panto-Agent：受电弓综合诊断

Panto-Agent 由两个子能力组成。

**滑板磨耗分类**

使用公开图像和迁移学习模型，建议至少对比：

- MobileNetV2；
- ResNet50。

最终部署其中一个模型，输出：

- 正常；
- 轻度磨耗；
- 明显磨耗；
- 低置信度拒判。

**电弧风险分析**

本期采用可解释的信号分析链：

```text
电压电流波形 → 滑动窗口 → 突变检测 → 高频能量分析
            → 事件持续时间和次数统计 → 电弧风险评分
```

如取得可用公开数据，再增加 1D-CNN 或时频图分类。

**Panto-Agent 综合判断**

将磨耗、电弧频次、电压电流波动和历史异常合并，输出：

- 当前风险；
- 关键证据；
- 建议复核内容；
- 建议处理时机；
- 是否生成工单。

### 5.3 Underbody-Agent：车底包覆结构与检查门检测

直接复用团队已有模型，完成工程化改造。

**检测内容**

- 检查门未关闭；
- 包覆板缺失；
- 结构错位；
- 异常开启；
- 明显外部异物。

**场景触发**

当车辆状态进入 `STATION_STOP` 或 `LOW_SPEED_PASS` 时允许调用。

**工程增强**

- 支持单张和批量图片；
- 映射车辆、车厢和检查门编号；
- 保存原图和标注图；
- 多角度结果一致性检查；
- 结果冲突时进入人工复核。

### 5.4 Wheel-Defect-Capability：车轮表面缺陷分割

**任务**

- 车轮区域分割；
- 剥落、变色、裂纹或划伤分割；
- 缺陷面积比例计算；
- 风险等级映射。

**模型**

优先使用 YOLOv8-seg 或 YOLO11-seg，避免引入过重框架。

**输出示例**

```json
{
  "component": "wheel",
  "defects": [
    {
      "type": "spalling",
      "area_ratio": 0.034,
      "confidence": 0.88
    }
  ],
  "severity": "WARNING"
}
```

该能力用于进站停靠或低速轨旁快检，**不宣称适用于高速运行中的细微缺陷识别**。

### 5.5 Cabin-Agent：车内开放场景巡检

**输入来源**

- 车厢摄像头；
- 顶部轨道巡检终端模拟视频；
- 乘务员穿戴终端；
- 上传短视频。

**处理流程**

```text
视频输入 → 截取4—10秒窗口 → 抽取6—8帧 → VLM多图结构化分析
        → 相邻窗口一致性检查 → Cabin-Agent规则校验 → 人工复核
```

**事件类别**

- 正常；
- 疑似烟雾或火光；
- 人员持续位于地面；
- 通道持续堵塞；
- 车门区域阻挡；
- 行李架物品伸出；
- 异常聚集；
- 疑似剧烈动作；
- 无法判断。

**技术要求**

- VLM 必须输出固定 JSON；
- 保留证据帧；
- 连续两个窗口一致时再升级告警；
- 低置信度时重新抽帧或人工复核；
- **不输出"确认暴力事件"等确定性结论**。

### 5.6 LineSide-Agent：线路侧能力

线路侧作为扩展模块，不与核心项目抢时间。优先选择一个能够直接运行的能力：

- 轨道区域分割；
- 线路异物检测；
- 接触网外观异常；
- 线路巡检图片 VLM 描述。

输入可以来自固定监控、人工巡检或无人机影像。无人机只是数据采集终端之一。

### 5.7 外部热加载演示模块

为展示平台开放性，额外准备一个轻量外部模块，例如：

- 车门状态模拟模块；
- 温度异常模块；
- 外部视觉分类模块。

该模块**不编译进主平台**，通过独立 Docker 容器启动，并自动注册到能力中心。

## 6. 多 Agent 与 Chief-Agent 设计

### 6.1 专业 Agent 职责

| Agent | 主要职责 |
| --- | --- |
| Drivetrain-Agent | 整合传动系统多个部件诊断 |
| Panto-Agent | 整合滑板磨耗、电弧和历史事件 |
| Underbody-Agent | 处理包覆结构和检查门视觉任务 |
| Cabin-Agent | 处理车内 VLM 任务和时序一致性 |
| LineSide-Agent | 处理线路侧图片和外部告警 |
| Chief-Agent | 全局风险融合、能力编排、RAG 和工单 |

### 6.2 Chief-Agent 工作流

```text
接收异常事件
    → 判断车辆和运行场景
    → 查询能力注册中心
    → 调用专业Agent或备用能力
    → 对事件去重和时间对齐
    → 进行多源风险融合
    → 查询RAG知识库
    → 生成带依据的处置建议
    → 等待人工确认
    → 创建工单草稿
```

### 6.3 风险融合

**风险等级不能由大模型自由生成，应由确定性风险引擎计算。**

考虑因素包括：

- 模型原始严重等级；
- 置信度；
- 事件持续时间；
- 一段时间内发生频次；
- 多个数据源是否相互支持；
- 当前是否处于运行中；
- 是否涉及关键部件；
- 是否存在历史未关闭工单；
- 模块当前可信模式。

统一风险等级：

```text
NORMAL / OBSERVE / WARNING / HIGH / UNKNOWN
```

### 6.4 冲突处理

两个能力结果冲突时：

1. 检查数据时间是否一致；
2. 检查能力是否适用当前场景和车型；
3. 比较能力可信等级；
4. 调用备用能力；
5. 仍无法判断时返回 UNKNOWN；
6. 强制人工复核。

## 7. RAG 知识库与数据库构建

RAG 不是单纯上传几个 PDF，而是构建一套具有**版本、权限、引用和业务对象关联**的混合知识数据库。

### 7.1 知识库目标

RAG 主要服务于三个场景：

1. 检修人员查询部件、异常和处置方法；
2. 专业 Agent 查询领域知识；
3. Chief-Agent 根据诊断事件生成有依据的建议和工单草稿。

**RAG 只负责知识检索、解释和建议，不负责直接判定安全风险等级。**

### 7.2 知识来源

**设备和检修知识**

- 受电弓结构和常见故障；
- 牵引电机、齿轮箱和轴承故障知识；
- 包覆结构和检查门相关说明；
- 车轮表面缺陷知识；
- 烟火、通道阻挡等车内处置说明。

**规程和标准知识**

- 可合法使用的公开铁路技术标准；
- 公开检修规程；
- 设备说明书；
- 安全操作要求；
- 项目自行编制的演示规程。

**案例知识**

- 公开事故和故障案例；
- 模拟诊断案例；
- 项目测试案例；
- 已关闭工单形成的经验记录。

**系统知识**

- 能力说明；
- 模型卡；
- API 文档；
- 数据字典；
- 系统操作手册。

### 7.3 知识库总体架构

```text
PDF、Word、Markdown、HTML、案例和工单
            ↓
      文档解析与质量检查
            ↓
      章节切分和元数据标注
            ↓
PostgreSQL结构化库 + MinIO原文件库
            ↓
      向量化并写入Qdrant
            ↓
     混合检索、过滤和重排序
            ↓
    Agent引用原文生成建议
```

### 7.4 文档处理流程

**第一步：文档准入**

每份文档必须登记：

- 文档名称；
- 来源；
- 文档类型；
- 版本；
- 发布时间；
- 生效时间；
- 适用车型；
- 适用部件；
- 审核状态；
- 文件哈希；
- 权限等级。

**第二步：解析**

支持：PDF、DOCX、Markdown、HTML、TXT。表格、标题、条款编号和页码尽可能保留。

**第三步：切分**

建议采用结构化切分：

- 按章节和标题切分；
- 规程按照条款切分；
- 普通文本每块约 400—800 个中文字符；
- 相邻块重叠约 50—100 个字符；
- 表格尽量整体保留；
- 每个知识块保留文档、章节和页码信息。

**第四步：元数据标注**

每个知识块至少包含：

```json
{
  "document_id": "DOC-001",
  "title": "受电弓检修说明",
  "chapter": "滑板磨耗",
  "page": 12,
  "asset_type": "pantograph",
  "fault_type": "strip_wear",
  "train_model": ["DEMO"],
  "version": "1.0",
  "effective_status": "ACTIVE",
  "permission": "INTERNAL"
}
```

### 7.5 RAG 数据库设计

**PostgreSQL 结构化表**

- `kb_documents`：保存文档级信息（文档 ID、标题、来源、文件地址、版本、生效状态、审核人、文件哈希、创建和更新时间）。
- `kb_chunks`：保存切分后的文本（chunk ID、document ID、标题层级、页码、原文、部件、故障类型、车型、权限、向量库 ID）。
- `kb_entities`：保存知识实体（部件、故障、症状、检测方法、处置措施、数据类型）。
- `kb_relations`：保存简单关系，例如：
  - 齿轮箱 → 可能出现 → 齿轮磨损
  - 齿轮磨损 → 可表现为 → 特定频段能量上升
  - 滑板磨耗 → 可能伴随 → 电弧频次增加
  - 检查门未闭合 → 处置方式 → 进站人工复核
- `kb_query_logs`：记录查询问题、检索结果、引用块、生成答案、用户反馈、使用模型、查询时间。
- `kb_feedback`：保存检修人员对答案的有效性评价，用于后续优化检索。

### 7.6 向量数据库

使用 Qdrant 保存：

- 文本向量；
- chunk ID；
- 文档元数据；
- 权限信息；
- 车型、部件和故障标签。

嵌入模型可采用中文和多语言表现较好的通用 Embedding 模型，并支持后续替换。

### 7.7 混合检索流程

只做纯向量检索容易遗漏专业术语，因此采用混合检索：

```text
      用户问题或诊断事件
            ↓
  提取车型、部件、故障和场景
            ↓
    PostgreSQL元数据过滤
            ↓
     向量召回 + 关键词/BM25召回
            ↓
      结果合并和重排序
            ↓
      选取高相关知识块
            ↓
     生成带引用答案
```

例如 Chief-Agent 收到：**CRH-07 受电弓电弧频次升高，同时滑板磨耗等级为严重**。系统先过滤 `asset_type=pantograph`，再检索电弧、滑板磨耗和处置建议相关知识。

### 7.8 RAG 输出要求

每条建议必须包括：

- 建议结论；
- 关键证据；
- 检查步骤；
- 建议处理时机；
- 引用文档；
- 引用章节和页码；
- 是否需要人工确认。

无法检索到可靠知识时，必须返回：

> 当前知识库中未找到足够依据，建议人工查询相关规程。

**不得虚构规程名称、条款编号和引用内容。**

### 7.9 知识版本管理

文档状态：

```text
DRAFT → REVIEWING → ACTIVE → OBSOLETE（或 REJECTED）
```

同一文档新版本生效后，旧版本保留但不参与默认检索。**历史工单仍需能够回溯当时使用的知识版本。**

### 7.10 RAG 管理页面

知识中心应支持：

- 文档上传；
- 解析预览；
- 切分结果检查；
- 元数据编辑；
- 文档审核和发布；
- 失效文档管理；
- 向量化状态；
- 检索测试；
- 引用追踪；
- 用户反馈统计。


```text

```

**外部能力热加载**


## 项目最终表述

> RailMind 是一套面向高速列车运行中、进站停靠及线路侧任务的开放式智能运维智能体平台。系统集成传动系统诊断、受电弓分析、车底包覆结构检测、车轮缺陷分割和车内 VLM 巡检等代表性能力，通过统一能力协议支持企业既有模块和第三方模型动态接入。Chief-Agent 依据车辆状态调度专业能力，结合结构化风险引擎与 RAG 知识库完成证据融合、规程检索、检修建议、人工确认和工单闭环，实现**模型可替换、能力可扩展、结果可追溯**的列车智能运维原型。
