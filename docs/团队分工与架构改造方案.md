# RailMind 架构改造与前端升级 · 团队分工方案

> 写给组长/项目经理用。目的：把这次改造切成能被独立交付、独立验收的几块，每块有人认领，块与块之间靠书面契约对齐。

---

## 一、先看清这次改造的实际盘子

在分组之前，先知道要动的东西有多大、哪些是真资产、哪些是欠账。

| 模块 | 现状 | 说明 |
|---|---|---|
| `railmind/core` | 2147 行 | 注册中心、风险引擎、工单、事件、RAG、Provider、编排 |
| `railmind/capabilities` | 3128 行 | 7 个能力适配器 + 共享的 `yolo_common.py` |
| `railmind/agents` | 726 行 | 5 个专业 Agent |
| `railmind/apps` | 361 行 | REST API + 演示事件 |
| `web` | 1406 行 | 其中 `index.html` 1112 行，含大量内联 JS 和写死数据 |
| `scripts` | 943 行 | 训练与评测脚本 |
| `tests` | 386 行 | **相对 core 明显偏薄，这是最该补的欠账** |
| `tools` | 21955 行 | 是 vendored 的 screenshot-to-code，**不是本项目代码，别当资产派活** |

两个必须先澄清的事实，否则分组会派错活：

1. **`web/app.js` 和 `web/style.css` 已经不存在了**，现在是 `dashboard.js` / `dashboard.css`。文档和项目结构快照里还留着旧名字。
2. **前端有一批"看起来是诊断结果、实际是写死的数字"**：传动健康度 92/78/61、四张波形图、车速 301、异物指标 0.699 和 2541 张。其中 0.699 只需要改成从 `runs/*/results.csv` 读就能变真。

## 二、分组原则：按接口切，不按目录切

最容易犯的错，是按代码目录分组——"你负责 capabilities，你负责 core，你负责 web"。这样分的后果是：每个人都在自己盒子里改，一到联调全乱，因为**没人负责盒子之间的缝**。

正确的切法：找到那些"能被独立交付、独立验证"的块，每块一个组，块与块之间用书面契约锁死。这个项目里天然存在四道缝（图纸里那四条虚线）：

| 契约 | 缝在哪 | 锁什么 |
|---|---|---|
| **A 训练与评测口径** | 数据组 ↔ 模型组 | 训练/验证集怎么切、标注规范、每个指标用什么真值算、复现命令 |
| **B 能力适配器 SDK** | 模型组 ↔ 平台组 | `capability.yaml` 字段、`sdk.py` 入参出参、失败与拒判怎么表达 |
| **C 工具与事件格式** | 平台组 ↔ Agent 组 | 工具签名、事件 JSONL 字段、工单状态机、错误码清单 |
| **D 前端接口与事件流** | 平台/Agent 组 ↔ 前端组 | 14 个端点的请求响应、SSE 事件序列、字段命名与单位 |

**这四条契约必须在开工第一周冻结成文档**。冻结之后，任何一方想改都要走变更——这是你作为组长最该亲自抓的事，比写代码重要。

## 三、六个组的职责

### 1. 数据与评测组（最容易被忽略，但决定答辩可信度）

**使命**：保证大屏上每一个数字都能追到出处。

**具体活**
- 盘点三套数据集：`datasets/`（约 1356 张图 + 26 个 mat）、`RailFOD23.v1i.yolov8/`（2541 张，4 类）、`高体受电弓设备目标检测数据集 YOLO格式/`（2676 张）、`第二届轨道交通比赛/`（1350 个 mat）
- 定标注规范、切分训练/验证集，**固定随机种子并写进文档**
- 维护训练脚本（`scripts/train_yolo26.py`、`train_fastener.py`）的可复现命令
- 建立**真值集**：电弧 19 个真实片段、SHM 已知冲击点坐标、扣件缺陷人工复核集
- 每周跑一次 `scripts/eval_capabilities.py`，把指标回填到指标表
- 把前端写死的异物指标改成读 `runs/*/results.csv`

**交付物**：一页纸指标表（含复现命令）、真值集清单、标注规范、评测报告 JSON

**对接**：给模型组喂数据算契约 A；给交付组提供验收用的数字

---

### 2. 模型与算法组

**使命**：把"看到了什么、多大把握"做准、做稳。

**具体活**
- SHM 冲击定位（当前 RMSE 40.99mm、能量 5 档准确率 90.5%）
- YOLOv8-pose 把手角度 + 盖板边缘判据（传统 CV，不是深度学习，别写错归属）
- YOLO26n 异物检测（mAP50 0.699）、扣件检测（mAP50 0.975）
- 受电弓滑板裁剪（内层模型）+ VLM 磨耗判级，含 <0.6 拒判
- 电弧信号链（去直流 → 突变检测 → FFT 高频能量，实测 19/19 检出）——**这是确定性信号算法，答辩时不要说成模型**
- 写能力适配器：`capabilities/*/adapter.py` + `capability.yaml`

**为什么适配器归这个组**：适配器的输出格式和模型语义是绑死的（能量档位怎么分、置信度怎么给、什么情况返回 UNKNOWN），交给不懂模型的人写会失真。

**交付物**：能力适配器（可在平台注册）、指标卡、失败样例集（每种至少 10 个反例）

**对接**：跟数据组对契约 A；跟平台组对契约 B

**注意**：`capabilities/yolo_common.py` 是异物和扣件共用文件，两个任务都会碰——**要么指定单一负责人，要么第一周就冻结它**，否则必出冲突。

---

### 3. 平台内核组

**使命**：守住全项目最有说服力的一条设计——**风险等级绝不由大模型生成**。

**具体活**
- 注册中心：5 种模式、心跳 TTL、主备切换、版本冲突校验
- 确定性风险引擎：阈值 <20 / <42 / <68，置信度抑制、降级封顶
- 工单状态机 DRAFT → OPEN → CLOSED/REJECTED，非法跃迁要拦住
- 事件与摘要双通道 JSONL 落盘
- 14 个 REST 端点 + SSE 事件流
- Provider 故障自动落 Echo 重跑
- 并发：5 线程同时打进来要串行化不错号
- **补测试**：现在 `test_risk.py` / `test_registry.py` / `test_engine.py` 覆盖太薄，改造期间要边改边补

**交付物**：API 契约文档（契约 D 的源头）、内核单测、错误码清单（`E_*` 必须有明确语义）

**对接**：收模型组的能力；给 Agent 组供工具；给前端组供接口

---

### 4. Agent 与 RAG 组

**使命**：让"下一步干什么"可解释、可回放、可复现。

**具体活**
- Chief 六步编排：find → invoke → consult → assess_risk + retrieve_kb → draft_workorder
- 工具参数由会话注入、不经大模型转手（这条设计很好，别丢）
- 大模型漏步骤时平台确定性补齐
- 5 个专业 Agent 的确定性分级
- 知识库：现在只有 12 条内置条目 + 关键词打分，查不到就固定拒答。**改造重点：扩条目、上向量检索、做版本化**
- 对话助手 5 类意图

**这里必须做的一个决策**：目前 Agent 的提示词是写给大模型看的，但运行时跑的是 Echo 确定性脚本——所以界面上"处置建议""复核要点"其实是固定输出。改造时只有两条路，**选一条并讲清楚**：
- 接真实模型，提示词真正生效；
- 或者明确声明这是"确定性规则引擎输出"，不装成大模型生成。

骑墙最危险，答辩被追问一句就穿。

**交付物**：编排 trace 回放工具、扩充后的知识库、拒答策略说明

---

### 5. 前端设计组（你原本就想到的）

**使命**：让每个数字都能点开看到出处。

**具体活**
- **拆单文件**：`index.html` 1112 行内联 JS 拆成模块化组件，这是改造的最大工程量
- 8 页大屏的视觉规范统一
- 对话助手悬浮窗
- 演示时间线
- **数据治理三件事**（优先级最高）：
  1. 传动健康度 92/78/61 —— 没有任何模型支撑，加显著"演示示意"标注或直接移除
  2. 四张波形图 —— 数学函数 + 随机数生成，图注要足够醒目
  3. 车速/里程/ETA —— 纯前端模拟，后端无数据源
- **统一演示时长口径**：README 写 48s、代码注释写 60s、实际时间线到 53000ms、toast 写 53s，四处不一致
- 进站快检图注的 85.4°/90.9° 是写死的，要改成跟当次推理结果联动

**交付物**：组件化前端、数据来源标注规范、演示脚本

**对接**：跟平台组对契约 D；跟 Agent 组对 `/chat` 与 SSE

---

### 6. 集成与交付组（横切，别让它变成打杂组）

**使命**：把五块拼成一个能演、能验收的东西。

**具体活**
- 端到端联调（每周固定一次，不是最后才做）
- 把 `pytest tests` 和 `eval_capabilities.py` 接进自动化，做成"改代码就出指标"
- 演示录屏与话术
- 验收用例执行（`docs/功能测试与评测方案V1.0.md` 那四层，约 50 条）
- 文档与答辩材料
- 环境一致性：确认 Python 解释器路径与 torch/cv2/fastapi 可用（README 记的路径与当前工作区对不上）

**它有自己的硬产出，不是给别的组补位**。

## 四、组长的活（你自己的职责清单）

1. **第一周冻结四条契约**，写成文档，之后变更走流程。
2. **守红线**：风险等级不由大模型生成、工具参数不经大模型转手。这两条是全项目最有说服力的设计，改造中任何一个组都可能无意破坏它。
3. **定义"什么叫做完了"**（DoD）：每个组交付物必须带可复现命令 + 一组反例，不接受"我这跑通了"。
4. **每周联调会**：不是汇报进度，是当场跑一遍端到端。
5. **决策"演示数据去留"**：哪些写死的数字必须变真、哪些允许留但要标注。这个决策只有你能拍板，工程同学会互相推。
6. **管住范围**：这次目标是"架构改动 + 前端升级"，不要顺手把模型重训一遍，那会把周期拉成两倍。

---

## 五、排期（四周版，人手充足）

| 周 | 重点 | 里程碑 |
|---|---|---|
| 第 1 周 | 冻结四条契约；数据组交指标表 v1；前端完成现状标注（哪些数字是假的） | 契约文档签字；假数据清单 |
| 第 2 周 | 各组分头改造；平台补内核单测；前端拆单文件 | 契约 A/B 可验证；前端模块骨架跑通 |
| 第 3 周 | 首次端到端联调；接自动化评测；替换写死数据 | 端到端跑通；指标自动产出 |
| 第 4 周 | 演示打磨、录屏、验收用例执行、答辩材料 | 冻结版本 + 验收报告 |

**六周版**：把第 2、3 周各拉长一周，第 4 周不变。第 5、6 周用于知识库上向量检索和编排 trace 回放这两个较大改造项。

## 六、团队规模怎么映射

| 规模 | 分法 |
|---|---|
| **6 人** | 一人兼两组：数据+模型、平台+集成、Agent+RAG、前端 2 人、组长兼契约与协调 |
| **10 人** | 每组 2 人：前端 3 人（工程 2 + 视觉 1）、模型 2、平台 2、Agent 1、数据评测 1、集成 1 |
| **15 人** | 数据组再拆"标注"与"评测"两条线，标注可外包；前端拆"组件开发"与"视觉设计"；模型组按能力再分（SHM/视觉/VLM） |

---

## 七、容易踩的坑

1. **按目录分组** —— 会导致"缝"没人管，联调期爆炸。
2. **把 `tools/` 当成项目资产** —— 那是 vendored 的第三方代码，2 万多行，别派给前端组。
3. **按旧文件结构派活** —— `app.js`/`style.css` 已不存在。
4. **不给评测组位置** —— 结果就是指标永远停留在文档里的旧数字，答辩没有证据。
5. **联调留到最后** —— 五块各自动了接口，最后两周全用来修不兼容，演示都做不完。
6. **Agent 组骑墙** —— Echo 脚本 vs 真模型，必须选一条并讲清。
