# RailMind 功能测试与评测方案（简明版）

> 更新：2026-09-17
> 一句话：这份文档回答两件事——**系统现在到底做了什么**，以及**这些东西分别该怎么验、验到什么程度算过**。

约定：下面命令里的 `PYTHON` 指项目用的 Python（README 写的是 `D:/Anaconda3/envs/railmind/python.exe`，跑之前先确认这台机器上路径对不对）。工作目录是仓库根 `D:\BB_zhongche\RailMind`。

## 第一部分：现在系统里有什么

按"一张图能干一件什么事"来数，一共四块。

### 1. 七个检测器（真正的 AI 模型部分）

| 检测器 | 吃进去什么 | 吐出来什么 | 目前水平 |
| --- | --- | --- | --- |
| 冲击定位 | 一段 Lamb 波信号（5000×8 的矩阵） | 两个冲击点的坐标，加上能量档位 | 位置误差约 41mm，能量分档准确率 90.5% |
| 检查门状态 | 一张车底检查门照片 | 两个把手各自的角度，判有没有关好 | 关门 0°、开门 85–91° 都能分开 |
| 受电弓磨耗 | 一张受电弓照片 | 磨耗程度：正常 / 轻度 / 明显 | 拿不准的时候直接说"不知道"，不乱判 |
| 弓网电弧 | 一段电压电流波形 | 有没有电弧、几次、累计多少毫秒 | 19 条真实电弧记录全部抓到 |
| 轨道异物 | 线路侧照片 | 有没有异物、在哪儿、多大 | mAP50 0.699 |
| 扣件缺陷 | 扣件照片 | 六种状态，断裂和缺失算最严重 | mAP50 0.975 |
| 车内巡检 | 一段车厢巡检视频 | 两个时间窗口各自的场景判断 | 缓存回放和实时分析两种模式 |

另外还有一个不对外暴露的小模型：受电弓部件检测，专门负责在磨耗评估前先把滑板那一块裁出来。

**判级规矩**（都是写死的规则，不是模型自己拍的）：冲击能量 ≥0.7J 算严重、0.35J 以上算重点关注；把手角度超过 75° 算异常、50–75° 算重点关注；扣件断裂/缺失直接最严重，移位翻转变形次之；异物占画面超过 5% 或者一次出现三处以上算严重；车内要两个窗口结论一致才升级，单个窗口异常只记观察。

### 2. 指挥中枢

一条事件进来，走固定的六步：找能力 → 调用能力 → 请这个领域的专业岗综合分析 → 算风险 + 查规程 → 需要人看的就开工单草稿。

几个刻意的设计：

- **风险等级不是大模型说的**，是规则引擎按"严重等级 + 置信度 + 一小时内出现几次 + 是不是在跑车上 + 是不是关键部件 + 有没有没关掉的旧工单"算出来的，每一步加分都写在理由里，能追溯。
- **数据不经过大模型转手**。大模型只决定"下一步做什么"，具体参数由平台从上下文里塞进去，避免它复述数据时瞎编。
- **兜底很硬**：大模型中途没走完，平台自己把缺的步骤补上；大模型整个挂了，自动切成本地脚本重跑一遍。
- 五个专业岗（结构、车下、受电弓、线路、车厢）各管一摊，做的事差不多：查这列车最近一小时有没有类似情况、按规矩定级、给出处置建议、附上规程出处。

### 3. 底座

- **能力登记表**：谁在线、什么模式（主用/备用/辅助/只看不用/停用）、平均多快、出错率多少。心跳 15 秒不到就判离线，主用挂了备用顶上。外部能力可以不重启平台直接注册进来。
- **风险打分**：上面说过了，规则全透明。
- **规程知识库**：内置 12 条，查不到就明说"没找到，建议人工查"，不允许编一条出来。
- **工单**：草稿 → 确认 → 处理完关闭，也可以驳回。
- **事件流水**：原始诊断和最终摘要分开存两份，都存在磁盘上，重启不丢，能按车号、部件、异常类型往回查。
- **两个后台线程**：一个定时模拟正常/观察级遥测，一个低频随机抽查几个能力真跑一遍并自动把工单走完——作用是让大屏看起来是"活的"。

### 4. 对外和门面

- 十四五个 HTTP 接口，除增删改查外还有对话接口和流式对话（SSE）。
- 大屏八个页面：综合态势、运行中监测、进站快检、车内巡检、线路侧任务、能力中心、知识中心、工单中心，外加一个运维助手聊天窗。
- **一键演示**：48 秒按顺序把七个能力挨个触发一遍，车速、里程、线路进度条同步动。这个是答辩主菜，建议全程录屏。

## 第二部分：怎么测

分四层，从"模型准不准"到"系统扛不扛造"。

### 第一层：模型准不准

一句话：**拿数据跑，看指标**。

已经写好了脚本，直接跑：

```
PYTHON -X utf8 scripts/eval_capabilities.py --repeat 5 --out data/eval_report.json
```

它会把七个能力各跑 5 遍，统计成功率、降级率、耗时中位数和 P95、严重等级分布、平均置信度，结果存成 JSON。某一个能力跑挂了（比如权重没找到、视觉模型没配密钥）不会中断整体，会单独记一条原因——这本身就是"降级不瞎编"的验证点。

各项具体怎么判过：

| 检测器 | 拿什么测 | 算过的线 |
| --- | --- | --- |
| 冲击定位 | 7 条 1.00J 样本，有复赛验证集就一起跑 | 1.00J 判成"严重"的比例 ≥85%；坐标落在板子范围内；不出 NaN |
| 检查门 | 关门图和开门图各一张 | 关门 ≤50° 判正常，开门 ≥75° 判异常；证据图确实生成了 |
| 受电弓磨耗 | 抽 10 张图，每张重复 3 次 | 同一张图 3 次结论至少 2 次一致；置信度低于 0.6 必须输出"不知道"，不许给等级；视觉模型不可用时标记降级 |
| 电弧 | 19 条真实记录 + 一条人为造的干净波形 | 19 条全部检出；干净波形一条都不许误报 |
| 异物 | 测试集全量 | mAP50 ≥0.65（现在 0.699） |
| 扣件 | 测试集全量 | mAP50 ≥0.95（现在 0.975）；断裂和缺失这类必须召回 ≥0.90，漏了代价最大 |
| 车内巡检 | 那段演示视频 | 缓存回放两个窗口都不能降级；实时重分析 3 次至少成功 2 次；没配视觉模型时要老实报降级 |
| 受电弓部件检测 | 对应测试集 | mAP50 ≥0.75（现在 0.768），保证裁剪那一步能用 |

三个 YOLO 的指标可以直接复现：

```
PYTHON -X utf8 -c "from ultralytics import YOLO; m=YOLO('runs/fod_y26n/weights/best.pt'); print(m.val(data='RailFOD23.v1i.yolov8/data.yaml'))"
```

### 第二层：流程对不对

一句话：**走一遍完整链路，看它该做的事有没有漏、不该做的事有没有干**。

已有 26 项测试，先跑一遍回归：

```
PYTHON -X utf8 -m pytest tests -q
```

要覆盖的点，按"测哪个零件"分：

**风险打分**
阈值边界（19/25/45/70 分别落在不同档）；高严重但低置信要被压下来；能力降级时最高只能到"重点关注"；能力离线直接判"不知道"并要求人工看；辅助模式一律要求人工确认；跑车上发生要额外加分。

**能力登记表**
缺字段、重复注册、低版本覆盖高版本，三种都要报错且报的是明确错误码；停心跳超过 15 秒要被判离线；主用停掉后备用要能顶上；设成"只看不用"或"停用"后不能被派活；连调 5 次后调用次数和平均耗时要对得上。

**工单**
走完 草稿 → 确认 → 关闭；草稿直接关要报错。

**知识库**
查一个肯定没有的词，必须回固定那句"没找到"，不许编。

**事件流水**
写三条不同车号/部件的事件后按条件查，只能查到匹配的，新的在前面；平台重启后事件和工单都还在。

**指挥链路**
WARNING/HIGH 事件必须出工单草稿，且工单上的风险等级和算出来的一致；低风险事件不许开工单；六个工具都要在调用记录里出现；专业岗输出的结论字段要全（结论、等级、置信度、处置建议、规程出处）；五个领域各跑一次，规程出处都得有编号；能力还没调用就去问专业岗，要报错挡住；能力离线时不能编结论，要老实说"拒判、转人工"；同一个域传不同输入（比如传图片 vs 传扣件图片）要分别命中对应能力；车内两个窗口结论不一致时只记观察、一致且是烟雾才升级，且不许出现"确认发生暴力事件"这种肯定表述；同一列车连发三次，频次加分要体现；五个线程同时打事件不能串号。

**降级**
配置一个连不上的大模型地址，看它会不会自动切本地脚本跑完；用一个"只走两步就收工"的假大脑，看平台会不会把缺的风险评估、查规程、开工单补齐。

### 第三层：接口和页面通不通

**接口**（用浏览器的开发者工具或者 curl 都行）：
健康检查要返回当前用的是真大脑还是本地兜底；能力列表里七个都在；九种演示事件各点一次都要成功，传个不存在的要返回 404；自定义事件能走完整链路并落盘；工单三种操作正常，传错 id 返回 404；重复注册返回 409；模式切换传非法值要有报错；对话接口传空消息返回 400；流式接口能收到一串事件（文字片段、工具开始、工具结束、完成）；静态页面和证据图能打开。

**大屏**（人工点一遍 + 录屏）：八个页面切换无 JS 报错；顶栏几个数字会随事件变；八个能力按钮点了表格要新增行、证据图能出来；一键演示 48 秒按序跑完七个事件、文案和动画同步；决策面板要能看到评分理由、专业结论和规程编号；车内巡检那页视频能放、两个窗口结论和证据帧都在、缓存和实时两个按钮都能用；工单页确认关闭后状态和闭环率要更新。

**对话助手**：问最近告警、问待办工单、问能力状态、让它演示一次受电弓电弧——四个都要答得出来且数据和对接口查的一致；断网时要明说"大脑不可用"，改成直查数据，不许编。

### 第四层：扛不扛造

- **耗时**：本地模型类连跑 20 次，P95 在 3 秒内；视觉模型类 P95 在 30 秒内；开真大脑跑完整链路 5 次，中位数 25 秒内（关掉深度思考的前提下）。
- **长跑**：服务开着放两小时（后台那两个线程也在跑），不能崩、不能内存一路涨、日志里不能有没接住的异常。
- **并发**：10 个请求同时打事件接口，全 200，事件和工单一一对应，没有重复 id。
- **乱输入**：空参数、错路径、坏图片、形状不对的矩阵、不存在的事件类型——都要返回明确的错误码，**绝对不许返回一个看起来像模像样的诊断结论**。
- **缺依赖**：把权重临时改名或者断网，能力应该以降级状态注册上去，平台照样能起来并且拒判转人工。
- **可复现**：`pytest tests -q` 全绿且完全不依赖网络。
- **数据**：`.env` 不能进仓库；含人员画面的演示视频只在本地用。

## 几个提醒

1. 视觉类那两个能力（磨耗、车内）结果有随机性，必须多跑几次看稳定性，报告里注明模型版本和温度参数。
2. 公开数据和模拟数据的验证不等于实车认证，报告里保留 README 那句免责说明。
3. 评测前把 `RAILMIND_DATA_DIR` 指到一个单独目录，别把演示数据搅乱；正式演示前可以用 `scripts/seed_demo_history.py` 预置一批历史。
4. 跑之前先确认 `python -c "import torch, cv2, fastapi"` 能通过，再批量执行，免得跑一半才发现环境不对。
