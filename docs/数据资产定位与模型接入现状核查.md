## 三、核查中发现的四个问题

### 1. 受电弓的指标，文档比实测写低了

- `docs/数据资产说明.md` 与 `docs/特征文件与训练分析.md` 都写 mAP50 **0.768** / mAP50-95 0.539 / P 0.751 / R 0.715。
- 实测 `runs/panto_y26n/results.csv`：第 30 轮同时也是 mAP50-95 最优轮，实际是 mAP50 **0.8095** / mAP50-95 **0.5935** / P 0.7585 / R **0.8052**。
- 影响：**文档写低了，白丢分**。参赛材料按实测值更正即可。不过也要注意，这反过来说明现有文档里的数字没有跟着 run 更新，其它指标同样值得复核一遍。

### 2. 部署的受电弓权重与训练产物对不上（答辩硬伤）

| 位置 | 体积 |
|---|---|
| `runs/panto_y26n/weights/best.pt` | 5.14 MiB |
| `runs/panto_y26n/weights/last.pt` | 5.14 MiB |
| **`railmind/capabilities/panto/weights/best.pt`** | **19.81 MiB** |
| `railmind/capabilities/lineside_fod/weights/best.pt` | 5.14 MiB |
| `railmind/capabilities/fastener/weights/best.pt` | 5.14 MiB |

同一个 YOLO26n 训练出来的权重，另外两个都正好 5.14 MiB，**只有部署到能力目录的受电弓权重是 19.81 MiB，大了 3.85 倍**。而 `wear_capability.yaml` 的模型卡里写的是「YOLO26n」。

这几乎可以断定：**部署的那份不是 `runs/panto_y26n` 的产物**，而是另一个更大模型（例如 s/m 档）或另一次训练的结果。

必须核实来源，否则就是「模型卡写的架构」和「实际跑的权重」不是一回事——这类问题答辩上被追问一句就很难圆。

### 3. 复现路径全部失效

- `runs/*/args.yaml` 里的数据路径指向 `D:\workspace\RailMind\...`，而当前工作区是 `D:\BB_zhongche\RailMind`。
- `fastener_y26n/args.yaml` 的数据指向 `E:\BaiduNetdiskDownload\铁轨紧固件损坏检测数据集 YOLO格式\...`（外部网盘目录）。
- `datasets/fastener/data.yaml` 里的 `path` 同样写的是 `D:\workspace\RailMind\...`。

后果：**现在按文档里给的命令重跑，会在读数据这一步直接失败**。解决办法是路径全部改为相对路径，或补一份环境变量说明；同时明确 fastener 用的是项目内 `datasets/fastener/` 这份压缩副本，而不是网盘原版。

### 4. 异物和受电弓其实是「从零训练」，不是加载预训练权重

对比三次训练的 `args.yaml`：

| 任务 | model 参数 | 含义 |
|---|---|---|
| fastener_y26n | `yolo26n.pt` | 加载了预训练权重 |
| fod_y26n | `yolo26n.yaml` | **从零开始训练** |
| panto_y26n | `yolo26n.yaml` | **从零开始训练** |

原因是下载预训练权重时 GitHub 不可达，脚本自动回退成从零训练（这一点 `特征文件与训练分析.md` 记了，但 `数据资产说明.md` 没记全）。

这正好解释了三者指标的落差（0.699 / 0.8095 对 0.975）：**扣件是有人扶的，异物和受电弓是从头学的**。

结论：**补上预训练权重重训，是最直接、成本最低的提升手段**。不要把 0.699 当成模型能力上限写进报告——那会白白低估自己。

## 四、没训练过的，该怎么评

三种情况评价方式完全不同，不能都套 mAP。

### （1）非模型类——按算法指标评，不按模型指标

**电弧信号链**
- 已有：真实记录检出率 19/19。
- 缺的是负样本：**正常波形误报率**。用牵引/制动正常段跑一遍，报警次数应为 0。
- 再补一项阈值敏感性：阈值上下浮动 ±20%，看结论稳不稳。信号算法的说服力主要来自这两项。

**远端视觉大模型（受电弓磨耗、车内巡检）**
- 各建 30~50 条的人工金标（磨耗等级 / 场景类别）。
- 指标：等级判对率、**拒判率是否落在合理区间**（拒判率过高说明提示词或图像质量有问题，不全是模型问题）、车内还要测**两窗口一致率**（因为规则是「两窗一致才升级告警」，这条规则本身要单独验）。

### （2）有权重但没指标——先补评测，再谈优化

**门把手姿态**
- 现状：ONNX 权重在，但工作区里没有任何指标记录。
- 要补三项：关键点 PCK（如 PCK@0.2）；**门板与把手同时检出率**（因为规则要求「必须同时检出 1 门板 + 2 把手，否则拒判」，这一条直接决定可用率）；角度判对率（≤50° 正常 / 50–75° 警告 / >75° 异常这条线判得准不准）。
- 另外，`capability.yaml` 写的训练来源是「LabelMe→YOLO 关键点数据集（团队自研）」，但这批数据不在工作区——**门把手的训练数据缺失，当前不可复现**，需要找回或重新标注。

**冲击定位**
- RMSE 40.99 mm / 能量 90.5% 来自复赛提交版本，证据在 `第二届轨道交通比赛/提交材料/semi-final/`。
- 要确认的是：部署的 `best_enhanced_model.pth` 与产出这份结果的模型是不是同一次训练。

### （3）数据集本身——只能评数据质量，不能评模型效果

- 已经有的（`docs/特征文件与训练分析.md`，可直接复用）：类别分布、实例总数、每图目标数、面积分档、bbox 极值。
- 还缺的：**标注一致性**（同一批图两人各标一遍，算 IoU 一致率）、负样本占比（无目标图有多少）、与真实线路分布的差距。
- 未训练的数据集若打算用来训练，正确做法是先跑一个 30 轮的 baseline 当基准，再谈改进——**没有基准就不要宣称优化了多少**。

## 五、训练好之后怎么接入平台

链路就是上面那张图的五步，落点是三个文件：**权重 + `adapter.py` + `capability.yaml`**。你们现在 5 个能力都已经按这套写完了，规范是现成的，新模型照抄即可。

### 技术栈（按现状 + 建议）

| 层 | 现在用的 | 建议 |
|---|---|---|
| 深度学习推理 | PyTorch (.pth) / ultralytics (.pt) / ONNX Runtime (.onnx) / HTTP 调远端 VLM —— **四套并存** | 检测类统一导出 ONNX 走 onnxruntime；冲击定位保留 torch；VLM 走 OpenAI 兼容 HTTP。把推理依赖从三套降到两套，部署和换机器都省事 |
| 服务框架 | FastAPI + Uvicorn | 保持 |
| 契约与校验 | `capability.yaml` + `sdk.py` + Pydantic | 保持，补权重 SHA-256 与训练数据版本号 |
| 落盘 | JSONL 事件流 + 证据图目录 | 保持，建议按日期归档 |

### 三条接入纪律（比技术选型更重要）

1. **换了权重必须同步更新 `capability.yaml` 的 model_card**（架构、数据版本、指标、哈希）。第三节第 2 条那个问题就是这条没守住造成的。
2. **置信度低于约定线必须走拒判**。现有「低于 0.6 转 UNKNOWN」的规则要保持，不允许模型硬给结论。
3. **演示数据与真实数据的指标必须分开写**。`capability.yaml` 里已经写了「公开/模拟数据验证不等同于真实高速动车上线认证」，这条要保住——它是加分项，不是免责声明。
